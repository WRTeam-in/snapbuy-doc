Payment Gateway

The app itself holds no payment credentials and no gateway toggle screen. Every gateway is configured and enabled in the Admin Panel, per country — the app only reflects what's turned on for the customer's selected country and drives the checkout flow.

Don't look for a settings screen in the app

There is nothing to configure inside the Flutter project for payment gateways — no API keys, no SDK setup files. All of that lives in the Admin Panel — Payment Gateways page, attached to each country's record.

Supported Gateways

The app's checkout screen can present any of the gateways enabled for the customer's country:

  • Cash on Delivery (COD)
  • Razorpay
  • Stripe
  • PayPal
  • Paystack
  • Midtrans
  • PhonePe
  • Cashfree
  • PayTabs

Which of these actually appear at checkout depends entirely on what's enabled for that customer's country in the panel — see the full credentials table.

How Checkout Works in the App

  1. At checkout, the app calls the backend to fetch the list of payment methods enabled for the customer's country.
  2. The customer selects one. Cash on Delivery completes immediately — no network round-trip to a gateway.
  3. For online gateways (Razorpay, Stripe, PayPal, etc.), the app opens the gateway's checkout using its official Flutter SDK or a secure in-app WebView, depending on the gateway.
  4. The customer completes payment on the gateway's own UI (card entry, UPI, wallet, etc.) — the app never sees or stores card details directly.
  5. On success or failure, the gateway redirects back into the app. Gateways that redirect via a browser (PayPal, PayTabs, some Stripe flows) return through the app's deeplink — see Panel URL & Deeplink.
  6. The app polls or listens for the order's payment status, which is authoritatively set by the backend once it receives the gateway's webhook confirmation — not by the app's own return-from-checkout event.

The app's return screen is not proof of payment

A customer can close the app mid-payment, lose connectivity, or background the app right after paying. The app returning to a "success" screen is a UI convenience — the order is only truly marked Paid once the backend receives the gateway's webhook. If webhooks aren't configured correctly on the panel side, orders can show as paid to the customer's bank but stay unpaid in the Admin Panel. See the Webhooks section of the admin payment gateway guide.

Deeplink Return for Redirect-Based Gateways

PayPal, PayTabs, and some Stripe checkout flows redirect the customer to a hosted payment page outside the app, then need a way back in. This return trip uses the app's custom URL scheme, configured in env/<environment>.json as DEEPLINK_SCHEME.

Without a working deeplink, customers get stranded

If the deeplink scheme isn't set (or doesn't match what's registered in the Admin Panel's Deeplink Settings), a customer who pays through a redirect-based gateway is left in the browser after paying — money taken, but no path back into the app. See Panel URL & Deeplink to configure and test this before launch.

Testing a Payment End to End

  1. In the Admin Panel, enable the gateway on your test country and enter its test/sandbox keys — see Test mode and live mode.
  2. Run the app (Basic Setup) and place an order using that gateway's test credentials (test card numbers, sandbox account, etc. — provided by each gateway's own documentation).
  3. Confirm the app returns cleanly to an order-confirmation screen.
  4. Confirm in the Admin Panel that the order shows as Paid, not just that the app showed success — this is what actually proves the webhook is wired correctly.

Tip

Test every gateway you plan to launch with, not just one — each has a different redirect/callback behavior, and a working Razorpay flow does not guarantee PayPal's redirect-based flow is also configured correctly.
